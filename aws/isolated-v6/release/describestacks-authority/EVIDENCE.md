## Authority and lifecycle decision

**Classification: AWS_DOCUMENTATION_OR_PROVIDER_AMBIGUITY + UNRESOLVED lifecycle authority risk.** There is a **conditional** gap if the delete handler invokes DescribeStacks under the proposed DeploymentRole: that role both lacks Allow and has an explicit boundary Deny for the action. The evidence does not establish the condition actually occurs. This is not a proven initial-create blocker. The registry lists the action for delete only; create/read/update lack it. Deletion, resource replacement cleanup, stack rollback and failed-create cleanup *may* reach the delete handler, but exact invocation/failure paths are unverified. Ordinary initial creation is not shown to require DescribeStacks.

The **expected principal**, if CloudFormation uses the planned runtime service role, is an assumed session of the new DeploymentRole under `cloudformation.amazonaws.com`. The proposed non-root recovery operator initiates or repairs stack operations and has its own stack-scoped DescribeStacks grant, but is not thereby the resource handler's principal. The V6 Lambda execution role handles runtime data-plane work and is not the expected CloudFormation handler principal. The bootstrap stack's initial operation may have a different approved recovery credential context; the ResourcePolicy resource is in the **runtime** template. These are design expectations; no live stack association or handler credential was observed.

**Resource scope:** the API/IAM reference supports a specific stack ARN, so `Resource: "*"` is not established as necessary. A narrow candidate could target `arn:...:stack/<approved-runtime-stack-name>/*` if the handler sends that StackName or its ID and authorization matches that ARN. If the handler omits StackName, the API documents an all-stack path and an additional ListStacks requirement; the current registry does **not** declare ListStacks. That makes a named stack plausible, still unproven. We cannot name the exact stack ARN/ID, infer the provider's parameters, or select a condition key safely. Account/region/name can be expressed in the ARN pattern after the target is proven; permission boundary and explicit Deny must be assessed together with the identity Allow. Session policies/SCPs can only narrow effective permission, not create a missing Allow.

**Why no permission change:** Adding DescribeStacks now would rely on an inferred provider request and assumed credential boundary. It could widen the role to new CloudFormation metadata and require changing both the identity policy and explicit boundary Deny. The safe target ARN and rollback credential context remain unverified. PR15's separate cfn-lint 1.40.2 versus 1.57.0 modernization stays separate. No validator warning is suppressed.

## What would close the question

1. Authoritative AWS-owned provider implementation or AWS service documentation explaining the delete handler's actual DescribeStacks call, request StackName and credential source; or future explicitly authorized sandbox lifecycle evidence (CloudTrail/stack events) with no legacy changes.
2. Approved account/region/runtime stack name and non-root service-role association. Verify actual effective IAM/SCP/boundary result for the chosen role and target ARN; simulation alone would be indicative, not a handler trace.
3. Only then review the smallest scope, managed-policy size and positive/negative tests for ordinary deletion and rollback. Do not deploy merely to gather this evidence under the current task.
