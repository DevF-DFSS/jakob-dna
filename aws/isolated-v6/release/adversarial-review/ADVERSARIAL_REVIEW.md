## Preserved role-reuse finding, now mapped to gate A1

The current runtime trust permits Lambda service assumption, and its data permissions/boundary permit V6 table GetItem/PutItem without a source-function condition. PR18's targeted IAM simulation supplies the missing `iam:PassedToService=lambda.amazonaws.com` context: the legacy user's PassRole to a hypothetical candidate execution role is **allowed**. A separate hypothetical function Create/UpdateConfiguration/Invoke is also allowed. The candidate table's known-legacy Deny tests the *acting role ARN*, not the human who passed the role. This supports a credible role-reuse path even if management of the V6 function itself were fenced. No role/function exists for these simulated ARNs; no role was passed or function invoked. See `aws-evidence.json` for requests/results and limits. This is a supported inference, not observed exploitation.

## Review verdict

The current candidate is **not ready for authorization**. The strongest new challenge is role reuse (P07): fencing the V6 function alone would leave a route to its table through the allowed execution role. This expands the existing authority blocker; it is not a request for broad new permissions. Gateway management (P08) must also be covered, not just Lambda invocation. Both paths are supported by targeted identity simulations, not observed exploits.

The proposition that a finite set of gates can permit a controlled experiment survives only after narrowing the claim to **phased, non-sensitive sandbox work**. Requiring all real Gateway/IAM/delete behavior before any resource creation is circular. Conversely, postponing authority over policy replacement, role reuse and emergency recovery until after creation is unsafe. [BLOCKER_CLASSIFICATION.md](BLOCKER_CLASSIFICATION.md) records the tested reduction: three prerequisite gates, six sandbox-test groups, three production groups and three accepted-limit/evidence groups. The 32 path tags (13/10/0/9) count different units. The current runtime template does not yet implement all proposed phase holds; the sequence is a future design requirement, not an executable or authorized procedure. No deployment is authorized by this distinction.

## Authentication challenge

The core can consume provider-independent Principal tuples. The AWS adapter is **provider-selectable with a strict compatibility profile**, not universally OIDC-provider-neutral.

| Field | Gateway responsibility | Local/binding responsibility and attack result |
|---|---|---|
| Signature, algorithm, `kid`, JWKS rotation | RSA-based algorithm/key/signature check; AWS documents key caching up to two hours. | No Lambda cryptographic verification. Provider rotation overlap and actual invalid-signature rejection are B tests. |
| `iss` | Exact configured issuer. | Exact string equality again; value unapproved. Provider key/issuer control is trusted. |
| `aud` / `client_id` | Configured audience match; `client_id` fallback only if aud absent. | Requires BOTH single-string aud and approved client_id. Default access token may fail safely; array-valued aud is rejected. |
| `sub`, tenant/sender/receiver/instruction | Projects provider claim; no candidate per-sub policy. | Principal `(iss,sub,client_id)` selects packaged binding; wrong sender/receiver/instruction denied. A label from request body never replaces binding. |
| `token_use` | JWT authorizer does not independently distinguish all access tokens from ID tokens. | Requires literal `access`. Provider must supply it; this is not universal OIDC semantics. |
| `scope` / `scp` | At least one route scope; each candidate route has one. | Requires scope string and matching unique jwt.scopes list restricted to read/write; scp-only or additional profile/email/admin scopes fail. No silent provider relaxation. |
| `exp`, `iat`, `nbf` | Documented timing checks. | exp/iat decimal strings required; optional nbf strictly checked if present. All claim values must be strings, so even unrelated array/object-valued claims can fail. Actual projection must be tested. |
| API, stage, route | Configured HTTP API routes and sandbox deployment. | Local event/API/stage/method/path checks; direct invoker can forge event values. |
| Alias | Integration targets sandbox alias. | Actual Lambda-supplied invoked_function_arn must match. A caller cannot replace this context via event JSON, but an admitted direct alias invoke naturally matches it. PR17 wording suggesting the real context itself is forgeable is too broad. |
| Source account/ARN | AWS service authorization context. | Full policy checks it; body/header values cannot set IAM context. Receipt ARN wildcards still rely on exact routes/parser. |

## Recovery and lifecycle challenge

The normal recovery policy is structurally narrow but is not operationally complete. It has no CreateStack/bootstrap IAM authority or publisher AssumeRole grant. Its UpdateStack/ContinueUpdateRollback RoleArn condition is supported by the current public CloudFormation IAM catalog; the real request must include/match the intended role. That condition does not validate template contents. A recovery actor able to update the runtime stack can change code and protections through the deployment role despite a direct Invoke Deny on the actor.

Bootstrap owns the API, bucket/policy and boundaries; runtime imports them. This avoids the artifact/API construction cycle. It does not solve authority bootstrapping: the independently approved recovery role and temporary bootstrap permissions must already exist before bootstrap creation. No second AWS account or administrator access is invented.

Retain on the bucket/policy, table and logs helps preserve evidence. It does not guarantee that rollback preserves a usable role, stack export or artifact delivery path. Lambda policy removal may precede failed function cleanup. The operator needs a preapproved containment/stop route and a plan for retained resources before first creation. The actual rollback/delete behavior, including PR16's declared DescribeStacks dependency, belongs in a bounded sandbox test. Neither the registry nor this review establishes an actual provider call; no speculative permission is added.

A separate lifecycle defect is supported by static source: changing issuer/client configuration alone changes no CandidateVersion property, and changing routes changes no CandidateDeployment property. With immutable published versions and AutoDeploy=false, DependsOn does not request a new snapshot. Configuration-only changes may leave an old alias/API deployment serving. This is not a demonstrated initial-create failure. A later remediation must deliberately version configuration/route snapshots and test rollback/revocation transitions. Packaged binding changes do change artifact bytes and CodeSha256, but they do not provide instant distributed revocation.

Sources: [CF rollback](https://docs.aws.amazon.com/AWSCloudFormation/latest/APIReference/API_ContinueUpdateRollback.html), [Retain](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html), [Lambda Version](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-lambda-version.html), [HTTP stages](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-stages.html). Source-function restrictions are a possible future identity-policy control documented by [AWS](https://docs.aws.amazon.com/lambda/latest/dg/permissions-source-function-arn.html); that key cannot be inserted into a resource policy and uses an unqualified function ARN. This review proposes no policy text or attachment.

## Controls that survived

- Current unconfigured bindings fail before SDK client construction; no ambient flag unlocks them. Positive synthetic gate completeness never flips deployment authorization.
- Wrong body/header sender or claim values do not replace server-owned bindings. Strict parsing, integrity, freshness and idempotency remain distinct local checks.
- Exactly two JWT routes; no default/ANY or Function URL resource. Stage depends on the full policy; no mixed Permission mechanism.
- Runtime/publisher explicit maximum-action/resource Denies block simple IAM escalation and named legacy access in the finite model. A permissions boundary grants nothing on its own.
- Immutable selected S3 object version plus artifact hash prevents a later PutObject version from silently replacing selected bytes.
- CI has no AWS credentials or write permission, checks exact source blobs, and correctly reports known lint failures. None of this proves AWS behavior.

These survive the isolated attack, not arbitrary code/admin compromise. All 32 credible or rejected paths, their evidence classes and limits are in ATTACK_PATHS.md / attack_paths.json. No path is labelled an observed exploit.
