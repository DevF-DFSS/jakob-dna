# PR17 evidence decision — 2026-09-26

Candidate behavior change: **NO**. `deployment_authorized=false`.

## Authentication: `ARCHITECTURE_COMPATIBLE_PROVIDER_MISSING` + `CONFIGURATION_REQUIRED` + `PROVIDER_BEHAVIOR_UNRESOLVED`

[AWS HTTP API JWT documentation](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html) says API Gateway checks RSA-based signature/JWKS `kid`, issuer, `aud` or fallback `client_id`, expiration, not-before, issued-at and at least one configured route scope, then projects claims to the integration. API Gateway has no candidate setting to require `token_use=access`, a separate approved `client_id`, a specific `sub`, or the candidate's exact `scope`/`aud` claim shape. The Lambda adapter performs those local checks, but does not verify the signature. If an invoker can bypass Gateway, the event and authorizer object can be forged.

The candidate requires **both** a single-string `aud` matching its approved audience and a separate approved `client_id`. Gateway would admit a client-id-only token if no aud were present, but the Lambda rejects it. This is fail-closed compatibility narrowing, not weakened authentication. A default Cognito access token includes client_id but documents aud only when resource binding was requested. Current Cognito resource-binding documentation supports a URL-form audience for human managed-login flows; it does not support M2M resource binding. Cognito custom scope names are resource-server-identifier/scope. Whether an approved Cognito configuration or other OIDC provider can deliver the entire exact `aud`, `client_id`, `token_use`, `scope`, `sub`, `exp`, `iat` and optional `nbf` profile in Gateway's integration claim shape still needs an actual provider decision and sandbox test. No provider is configured in the two sampled regions. No token was issued or tested.

The HTTP API Lambda payload v2 reference shows `requestContext.authorizer.jwt.claims` and `.scopes`, API ID and stage. This supports the candidate's expected envelope *shape*, but not guaranteed representation of every provider-specific claim or live Gateway enforcement. API Gateway's scope rule is **at least one** required route scope; the candidate defines one scope per route, then Lambda and ingress require the exact operation scope. API Gateway supports `scope` or `scp`; Lambda specifically requires `scope` and an exactly matching list projection, so an `scp`-only provider remains incompatible. Missing or malformed claims fail closed. The provider-neutral binding registry remains empty/unconfigured, which prevents startup.

## Containment: `KNOWN_BYPASS_PATH` (control-plane policy replacement) + `LEGACY_AUTHORITY_RISK` + `EFFECTIVE_POLICY_UNRESOLVED`

The new function policy *intends* to deny direct IAM invokers through `DenyNonGatewayInvoke` on function and qualified ARNs, and to deny known legacy principal ARNs for supported Lambda resource-policy actions. [IAM IfExists semantics](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html) say a Deny with `StringNotEqualsIfExists` applies when the key is absent. [PrincipalServiceName guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html) says that key exists for a direct AWS service-principal request. That supports the static intent: ordinary IAM direct invoke should meet the Deny; API Gateway service invocation should be evaluated against its service name, source account and exact source ARN. Real context and unqualified/version/alias evaluation are untested. [Lambda documentation](https://docs.aws.amazon.com/lambda/latest/dg/access-control-resource-based.html) says an unqualified full policy applies to the entire function, but live alias/version enforcement remains a test gate.

A live read-only policy retrieval shows `us-os-gateway` currently has managed `AWSLambda_FullAccess` v7 with `lambda:*` on `*`, no user boundary and no observed Organizations membership/SCP path. A single-resource IAM simulation on a hypothetical V6 `:sandbox` alias returned **allowed** for `lambda:InvokeFunction`, matched to that managed policy. This is an identity-side result only. It omits the candidate's not-yet-existing Lambda resource policy and does not prove successful direct invocation. More seriously, the same managed policy grants `lambda:PutResourcePolicy`, `DeleteResourcePolicy`, `AddPermission`, `RemovePermission` and `UpdateFunctionConfiguration`; AWS's [supported resource-policy action list](https://docs.aws.amazon.com/lambda/latest/dg/access-control-resource-based.html) does not include those management operations. The candidate's explicit Deny therefore cannot be claimed to fence the existing user from replacing/removing its future function policy. After removing protections, identity-side InvokeFunction authority provides a plausible direct-bypass path. This is a **known design gap** under the observed current identity policy, not an observed live bypass. Function creation precedes policy attachment, leaving a separate creation window.

Two legacy execution roles' hypothetical identity simulations returned implicitDeny for InvokeFunction but allowed DeleteFunction; Jakob role returned implicitDeny for tested Lambda actions. Those results are neither complete effective-policy proof nor complete principal inventory. Account root/sufficient administrator can replace protections. The proposed deployment role is intentionally authorized to manage candidate code and policy but has not been created; recovery role is unconfigured. No V6 function, alias, Function URL or API currently exists in the two sampled regions. No Function URL resource is defined in the candidate. The account root connector was used only for reads.

**No candidate runtime/template/IAM edit is made in PR17.** The broad existing user's identity authority cannot be removed by narrowing a new execution role. Changing legacy IAM is outside this task. The current evidence supports a pre-activation blocker: review and separately authorize a narrow legacy-identity fence or stronger account separation; verify effective management and invoke denies, service context and creation-window controls before a live sandbox negative test. A successful static policy test or green unit suite cannot satisfy this gate. PR15 validator modernization and PR16 DescribeStacks ambiguity remain separate.
